# Start here

His skills live in Gucixdev/claude-skills (public; the personal ones sit in a private repo), one small skill per concern. Each header carries `priority`, `tags`
(hashtags) and `requires` (what it needs: other skills, commands, libraries, MCP servers...). The standard and the
tooling are in `skill-everything`.

## How to use them

1. Now: load every priority-0 skill below. They are short and apply to everything.
2. When a task starts: match its words and its hashtags against the list (or `bin/skills ls '#tag'` in the repo) and
   load the matching priority-1 and priority-2 skills. Priority 3 only when he names it.
3. Load what a skill `requires` (`skill:` entries) along with it. On his machine `bin/skills req NAME` checks the
   commands, libraries and servers too; a missing optional (`?`) one means use its fallback.
4. Two skills disagree: the lower priority number wins. His explicit instruction in the session and a repo's own
   CLAUDE.md beat every skill.
5. A lesson worth keeping comes up: add it to its skill or make a new one (`skill-everything`).

Where they load from: on his machine `~/.claude/skills` (linked by `bin/skills install`); in a cloud session with this
repo attached, its `.claude/skills`; otherwise clone Gucixdev/claude-skills and read `skills/` (his preference says so).

## Source of truth: the graph, then GitHub

Two places hold the truth, in this order (his words, 2026-11-22: use the graph mainly, push it hard; and "wolę pushować
niż na dysku kisić"):

1. **The graph** (graphify, `mcp__graphify__*`; deferred tools, load them with ToolSearch). Every lookup of "where is
   X / what calls Y / what does this touch" starts with `query_graph`, `get_node`, `get_neighbors`, `shortest_path`,
   `god_nodes`, before Grep or a whole-file Read. Grep only for what the graph does not answer, and when it lacked
   something, say so and refresh it. A path from the graph is a hint: read the file before editing.
   - One graph per repo, built with `tools/graphify-sync` (`graphify update`, tree-sitter, free, no LLM, seconds). The
     repos it keeps are listed in `~/.config/graphify/repos`; `graphify-sync -l` shows each graph's age. Query a repo
     with `project_path=/abs/repo`; the server's default graph is only the one it was started with.
   - Keep it growing: after a batch of code lands (a commit, a new module, a move or rename), run `graphify-sync` for
     that repo before the next lookup, and add a new repo to the list the day it is created. A graph older than the
     last big move answers wrongly (2026-11-22: the holyc graph still listed paths that were gone), so refresh first.
   - Notes and decisions worth keeping go into the graph as nodes only through its own tooling; until then they are
     memory and `todo.md`. Later we build our own graphify in TypeScript on the same `graph.json` format (todo.md).
   Graphify in every phase of a repo (his words, 2026-11-22: "przy kazdym repo zaczynasz od grafu, zmiany tez graf, push
   tez graf, wszystko graphify"):
   - Start: a repo not yet in `~/.config/graphify/repos` gets added and built first, then asked, before any find/grep.
   - Change: before an edit, `get_neighbors` / `query_graph` on the symbol shows its callers and consumers, so none is
     missed; after the batch, `graphify-sync` again and one query that confirms the new code is wired in.
   - Push: refresh the graph, check what the commits touch (`get_pr_impact` or neighbors of the changed symbols), say
     which consumers were looked at. `graphify-out` stays out of git (`.git/info/exclude`), the graph is a local tool.
2. **GitHub.** A finished, committed piece goes to origin soon after the commit, not after a pile builds up on the
   disk. The standing go-ahead and its limits are in `rules (discipline)`.
